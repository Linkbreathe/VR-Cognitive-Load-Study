## Main conclusion

There is evidence of an upstream stale-eye symptom and separate application-side risks. Neither the current overlay nor the integer countdown has been established as the cause of the afternoon failure. Rejecting bad gaze can make an upstream problem visible; it does not necessarily cause that problem. Conversely, the angular freeze heuristic can reject fresh small movements, so an `EYES FROZEN` message alone does not locate the fault.

The existing three native-layer files were re-read: each has 300 successful location calls, flags 15, and exactly one eye timestamp. Thus all 900 observations repeat a timestamp despite tracked flags. These are historical engineering recordings, not a new live test. The earlier USB interruption and reconnect remain temporally associated with the afternoon transition, not a proven cable cause. See [the corrected timeline](EyeFailureTimelineReview.md) and [native freshness review](EyeInputRecoveryReview.md).

## Findings and investigation priority

| Priority | Finding / trigger | Effect and evidence boundary | Recommended next work |
|---|---|---|---|
| High | Runtime supplies cached eyes while head tracking moves. | Existing native records establish repeated timestamps. A head-relative frozen ray naturally follows the head in world space. Sensor, transport and runtime causes are not separated. | Compare advancing native sample time and independent eye-in-head motion across a controlled Link reconnect, with a still-head target check. Keep raw rejected samples separate from valid evidence. |
| High | Angular freeze logic overrides fresh timestamps. | `EyeFreezeDetector` rejects movement below 0.1 degrees after about 1.8 seconds of coverage. The isolated audit fed advancing timestamps and bounded 0.02-degree movement: freshness was true while frozen was true (spread 0.02798 degrees). This establishes a software counterexample, not the real-world false-positive rate or the cause of the earlier failure. | Separate timestamp staleness from low angular variation. Validate any change using real fixation and deliberate eye movement; do not remove safeguards merely to increase valid coverage. |
| High | Freshness and compatibility coverage differ by execution mode. | `QuestLinkEyeSpaceFeature` initializes only in the Editor from an enabled local engineering config; native time gating additionally requires runtime name `Oculus`. Participant startup, standalone Windows players and Android do not inherit this path. If the previously observed eye-space error recurs outside it, there is no equivalent retry. | Treat each deployment path separately. Decouple any future production acquisition support from debug-overlay permission, with versioned acceptance. Do not assume engineering success proves participant/Android support. |
| High | Head validity is not a per-sample gaze gate; reference-space recovery is incomplete. | `SampleGaze` checks the eye device but uses `head.localRotation` and `head.parent` without requiring current head tracking. `HeadsetTracked` gates comparison preparation only. The project does not subscribe to `trackingOriginUpdated`. A head/reference-space loss or recenter can therefore invalidate the coordinate assumption without necessarily invalidating a reported eye pose. | Record head validity, reference-space changes and reconnects together. Require a new coordinate check after discontinuity; avoid silently moving the task during a scored round. |
| Medium | Angular guard resets on invalid input or a gap over 250 ms. | An invalid observation clears history; the first valid return is not frozen until sufficient history accumulates. The audit reproduced this state transition. Native time gating covers unchanged timestamps only where that additional path is active. | Do not use one transient white reticle or one `TRACKED EYES` status as sustained recovery. Validate reacquisition before granting readiness. |
| Medium | Preparation readiness differs between practice and comparison. | `ComparisonTrackingReady` returns true for non-comparison modes; comparison uses the latest status without a sustained validation interval. Practice can therefore start with absent eyes, while comparison waits. This is current policy, not proof of a damaged tracker. | Make preflight diagnostics explicit and test both paths. Any stronger task gate is a protocol change requiring deliberate implementation. |
| Medium | Eye pose, native timestamp and head pose are separate reads. | Legacy XR gaze is read first; a separate native locate supplies timestamp/flags; head pose comes from Input System's `TrackedPoseDriver`. Their temporal coherence is not logged. The real driver uses `UpdateAndBeforeRender`, while gaze is sampled during controller Update. Moving-head discrepancies and display latency are possible; their magnitude has not been measured. | Capture corresponding pose/time/space identities in one engineering diagnostic and compare them. Native timestamp progress is not an absolute-latency measurement. |
| Medium | Reticle surface hit and logged target use different geometry. | The reticle uses a physics hit plus sphere bounds and an unbounded movie plane, even when the movie is hidden. Logged classification uses padded sphere/tray bounds, task priority, then a bounded movie rectangle; it does not test arbitrary scene occlusion. Thus the visible ring can land at a surface that does not match its interpreted target. | Audit representative sightlines, screen edges, inactive video and occluders. Label the ring as a display aid; do not interpret it as authoritative ROI evidence. |
| Medium | Task ROI is larger than the visible sphere. | Current v5 uses the sphere/tray union with 4 cm padding. During running trials a visible tray keeps the task region active even when the sphere is hidden. Looking near/on the tray can count as task. This follows the unified task-area policy. | Preserve the version and denominator. Do not interpret task fraction as exact sphere fixation or compare it directly with old sphere-only sessions. |
| Medium | Sampling and logging can lose temporal detail. | Scheduling uses `nextGaze = now + 1/30`; it is a maximum-rate frame sampler, not a 30 Hz acquisition clock. At a steady 72 fps it normally samples every third frame, about 24 Hz. Main-thread auto-flushed rows, allocations, archive scans and hashing can add load; no profiling demonstrates that they caused the freeze. | Measure actual sample intervals and frame gaps under video/EEG/archive load. Do not use these records as native-rate saccade measurements. Preserve missing coverage rather than filling gaps. |
| Low | Display state can be mistaken for tracking state. | White means accepted input; amber draws rejected raw input; gray holds a world-space point. Before any sample there is no held point. A world-space point can leave the field of view. A faint persistent sphere outline does not indicate valid eyes. Current local config has both overlay switches false. | Check effective overlay settings and source color before diagnosing invisible/fixed markers. Keep participant overlays forbidden. |
| Low | Error reporting can obscure the first failure. | When native metadata is unavailable, `eyeFreshness.Status` takes precedence over earlier `NO EYE DEVICE` / `EYES NOT TRACKED` status. Rapid status transitions are also rate-limited in event logging. | Expose acquisition, native metadata and angular evidence as separate diagnostic fields. Do not infer a single root cause from the final status string. |
| Low | Boundary and visualization denominators differ. | Gaze sampling occurs before `Render()` updates sphere visibility, so an onset frame can contain the previous renderer state. Trial CSV summaries count samples; Guard and Console aggregate capped durations. Console projects onto the front wall, not the headset image, and its layout follows head position. | Treat a boundary-frame discrepancy and different percentages as separate from sensor failure. Review identical windows and denominators when comparing displays. |
| Low / unresolved | Virtual Desktop implicit layer is registered enabled. | Host registry contains `XR_APILAYER_VIRTUALDESKTOP_oculus_compatibility`, DWORD 0. No relevant shell/user/machine override was found. Registration is not proof of active interception; the Editor was stopped. The upstream project describes activation for OculusXR applications using SteamVR and Virtual Desktop, unlike the current Meta runtime / Unity OpenXR configuration. | Keep as a controlled differential variable only if runtime evidence warrants it. No layer was disabled or removed. |

## Checks without evidence of a current configuration conflict

- Loaded Standalone settings: Eye Gaze Interaction, Oculus Touch, Touch Pro and the engineering compatibility feature enabled; retry enabled. Android: Meta Quest support and Eye Gaze enabled; engineering compatibility absent/disabled as designed. No enabled mock runtime, foveated rendering or API-layer feature was found in these lists. Only the OpenXR loader is referenced for each platform.
- The loaded scene has one enabled head `TrackedPoseDriver`, XR HMD position/rotation bindings and tracking-parent scale (1, 1, 1). Additional Unity Editor executable processes inspected were asset-import workers, not a second scene controlling this headset.
- Windows active runtime points to Meta's `oculus_openxr_64.json`; project-local Oculus preview is enabled. Current local config is engineering / operator-managed / Quest Pro, with both overlays disabled. This says nothing about previous assignments or whether a headset is currently worn.
- The installed Unity OpenXR 1.19 source explicitly supports the legacy `gazePosition`, `gazeRotation`, `isTracked` and `trackingState` usages used here. Using those features is not itself an unsupported-binding error.
- There is no custom Android manifest at the usual project path, but the installed Meta build processor adds eye permission and the eye feature when Quest Pro and the eye extension are selected; the relevant settings are present. No APK/merged-manifest verification was performed.
- Overlays only consume gaze; they do not write input poses or feed back into classification. The custom shader includes stereo instancing support. Optical readability, binocular comfort and real device rendering remain untested here.
- Desktop comparison uses explicitly marked simulated aggregates; it does not synthesize raw tracked-eye positions or silently replace failed Quest Pro input with head-forward gaze. Guard aggregation caps sample duration at 100 ms and accounts for missing time.
- EEG processing runs through the separate service path. No direct EEG-to-XR pose write was found in the inspected acquisition/control code. Shared PC/USB load and the physical fit of Mindtooth plus the headset remain untested possible interactions, not established electrical or software interference.

## Physical and operating-system uncertainties

This audit cannot exclude headset fit/calibration, glasses/lens condition, eye-camera visibility, headset-side permission, USB port/cable/power behavior, Link transport, runtime/firmware defects or sustained video/CPU/GPU load. These require controlled device observations. The user's earlier report of no wearer, fit or chair change is preserved; none of those changes is asserted as the afternoon cause.

The next useful engineering sequence is: confirm fresh timestamps and independent eye motion with a still head; compare head movement while fixating a known target; repeat in practice and comparison; then test a planned Link reconnect and full media/EEG load. Record native time, raw eye/head poses, reference-space changes, sample gaps and accepted ROI together. Keep these runs outside participant data. An optional later process-scoped implicit-layer comparison should be used only after a baseline exists, with the original environment preserved.
